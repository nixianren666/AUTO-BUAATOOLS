## 5. 源码审阅发现与长期运行风险

以下与上述 Mock 结果不同：代码路径已确认，未全部在线复现。

| 维度 | 发现 | 影响与后续核查 |
| --- | --- | --- |
| TLS | iClass 与 Boya 客户端都设 verify=False；直连签到还有 HTTP 回退 | 与 README 的强加密保障文案不一致；证书校验/兼容策略需明确，不能声称所有链路均受有效证书验证 |
| 本地秘密 | AES key 与 IV 由公开常量固定推导；加密失败返回明文 | 是可逆的静态编码，不能宣称等同系统凭据保护；需检查异常路径和保存策略 |
| 学期/分页 | 已选查询截止 2027-01-01；后台课池最多拉三页 | 长期使用可能漏掉以后课程或第四页以后内容 |
| 策略口径 | 自动候选缺口使用推算校历、按已选数计数；UI 统计优先官方学期且按通过计算 | 两种口径不是同一指标；需要明确规划数与完成数，遵守官方学期元数据优先 |
| 冲突 | 自动抢课只遍历已选博雅；课程时间无法解析时视为无冲突 | README 宣称也对比常规课堂，与实现不符；未知时间应有保守行为 |
| 防重 | 课程名与 ID 同时作为防重索引；状态集合未见定期清理 | 同名不同课程、退课再选、账号删除再加、跨日跨学期和长时间内存增长需专门测试 |
| 认证 | 博雅签到/签退捕获一般异常并计入三次失败，会话过期没有在该路径即时续期 | 认证故障可能耗尽当天次数；应区分认证恢复和业务失败 |
| 时间 | 调度与 parse_dt 主要使用无时区 datetime；格式裁切不保留偏移信息 | 非北京时间宿主、跨日、请求延迟和 DST 场景需验收；不能靠 Docker 的 TZ 覆盖所有客户端 |
| 并发 | 普通调度一个 async 循环，博雅一个线程依次遍历账号 | 账号状态隔离成立，但 README“每账号独立线程”的文案不符；慢账号会拖延后面的账号 |
| 主循环 | async API 路由直接调用同步 Boya HTTP；v1.3 add_log 同步推送微信，单次可等 15 秒 | 可能阻塞事件循环/关键操作；日志通知不应拖住签到时序 |
| 账号切换 | 前端无响应代次检查；后端 active_username 是全局值 | 并发请求和多浏览器视图需要核对账号上下文，不能仅靠前端先改标题 |
| 手动边界 | 手动博雅 API 缺少完整窗口/配置校验，缺点时回退固定坐标 | UI 隐藏按钮不能替代 API 参数与状态校验；本次未调用真实打卡 |
| 自启 | Linux UI 控制用户服务 buaa-signin；安装脚本操作系统服务 auto-buaa；Mac 文件存在被用作启用依据 | 开关/卸载/状态可能与实际服务不一致；systemctl 失败值也不能被忽略 |
| 更新 | Linux/Mac 服务 update 拉取 main | 当前 main 仍属撤回系列；稳定部署更新可能重新引入已撤回功能 |
| 安装/卸载 | Inno 卸载规则递归清除整个安装目录的内容 | 选择已有共享目录时可能删除其他文件；未执行卸载实验 |
| 版本与宣传 | health=1.2.5、免责声明=1.2.2、Mac plist=1.2.5、CLI 旧版本、README 旧开关/心跳文案 | 应统一版本来源并修正文案，不能靠版本徽章判定发布一致 |
| 源码/分发管理 | Git 直接跟踪多代 EXE，没有产物与 commit 的统一清单 | 同一名称、时间戳和成功上传不足以证明同版；后续需要内容哈希和来源 commit |

## 7. 接管后的执行顺序

1. 继续以 v1.2.6 作为业务基线，保留当前 UI 原型和用户配置。首先厘清目录、默认 EXE、源码与远端的对应关系。
2. 优先修共享业务中的时间边界、学期判定、账号异常隔离、请求竞态与资源释放；把本次复现场景转为有意义的回归测试，再做六层级联检查。
3. 明确 TLS、管理面访问与凭据保存的实际保证；更新与实现不符的安全宣传。
4. 修构建版本来源、Release 目标和错误吞掉；安排每平台实际验收，生成带 commit 与哈希的产物清单。解决流水线之前，不再把“上传完成”写成“同版全平台已交付”。
5. UI 工作从已保存的液态玻璃通透度原型继续，先获得视觉与交互验收，再接正式业务。微信保持撤回状态。

这是后续任务的依据与建议顺序，未在本轮自动执行代码修补、删 Release、改标签或发布。接管文档已经连接这份审查，新的项目对话可以直接读取证据和待处理项。
